# Inline compression benchmark - 2026-10-18

**Setup.** Server: 64 cores, 123.52 GiB of RAM, `hz 10`. Client configuration: 512 connections, 16 threads. Load: 5M `SET` over `1M` unique keys, `github-events` JSON values (10K unique values) of 2KiB bytes on average (1.90 GiB of values). Then 10 minutes without load, then 4 runs of 5M `GET` at a limit of 100,000 rps: the first `10%`, `30%`, `50%` of the keys, then `all keys`, in this order.

> Values: Real world values: 10,000 GitHub events, sampled from the GH Archive hour 2024-01-01-0 (https://data.gharchive.org/2024-01-01-0.json.gz), each used for about 100 keys.

## Findings

1. **Memory -50.8%** (`cursor-base`: `used_memory` 2.17 GiB -> 1.07 GiB; 0.89 GiB saved on 1,000,000 values). All cursor scenarios with 500 samples and at least 1000 in-flight requests reach 1,000,000 compressed values, with t99 between 336 and 367 s.
2. **cursor needs far fewer checks than random.** cursor-base: 2,800,451 keys checked for 100%. random-samples2000: 11,802,752 for 99.99%. random with 500 samples: 2,988,000 checks, 89.7% compressed after 600 s (t90 not reached).
4. **compression-threads did not make a big difference:** 4, 12 and 16 give t99 367, 362 and 342 s. All 1M values need 4.20-4.46 s of worker CPU in total. The sweeper uses 9.01 s of main-thread CPU in the 600 s window (cursor-base), against 1.29 s for baseline-off.
5. **SET is not affected:** 882,556-923,813 rps, p50 0.477-0.487 ms, p99 2.863-3.055 ms in all io-threads-12 scenarios, against 892,003 rps, p50 0.485, p99 2.959 for baseline-off.
6. **GET latency follows the number of first reads of compressed keys.** cursor-base, p99: 0.819 ms (100,000 decompressions, 10% run), 1.383 ms (211,911, 30%), 1.479 ms (219,698, 50%), 2.831 ms (597,825, 100% run), against 0.771 / 1.503 / 0.401 / 0.457 ms for baseline-off. p50 stays between 0.16 and 0.429 ms. The four cursor-base runs keep 99,957-99,965 rps.
7. **One full read removes the whole saving.** `used_memory` at the end is 2.14-2.17 GiB in every compressed scenario, the same as before compression (2.17 GiB).

## Recommendations

1. Keep `cursor` as the default policy and 500 samples. 2000 samples reach t99 in 209 s instead of 362 s, but GET p99 rises from 2.831 ms to 10.559 ms in the full read.
2. Raise the default of `compression-max-inflight-requests` from 100 to 1000.
3. Make read latency the next design topic: decompress in the I/O threads, and a read of a cold key that returns a temporary copy and keeps the frame, so one scan does not undo the saving.
4. Add scenarios with `--activedefrag yes` (at least `cursor-base`, `cursor-if100`, `random-base`), to measure the RSS saving with partial compression and the CPU that defrag costs. Results of `cursor-if100` and `cursor-ct4` with defrag: `RESULTS-2026-10-18-defrag.md`.
5. Add a run of 1 hour without reads for the backoff, and a run with smaller values (allocator rounding, design doc Appendix A).

## Knobs

| Knob | Kind | What it does | Values in this run |
|---|---|---|---|
| `--io-threads` | Startup | Number of Valkey I/O threads. They read requests and write replies for the clients; the main thread still runs every command. More threads give more network throughput. | 6, 12 (base), 24 |
| `--compression-mode` | Startup | Turns inline compression on, and names the algorithm. `off`: no compression, no sweeper, no workers. | `off` (baselines), `lz4` |
| `--compression-threads` | Startup | Number of worker threads that compress the values. The main thread copies a value into a job; a worker compresses the copy; the main thread installs the result. | 4, 12 (base), 16 |
| `--compression-max-inflight-requests` | Startup here (also runtime) | The most compression jobs at the same time: queued, running, or done and not installed yet. When it is full, the sweeper does not pick new values. Each job holds a copy of the plain value. | 100 (the default in this build; 1000 since `88ab7a8fe`), 1000 (base), 10000 |
| `compression-sweeper-policy` | Runtime | How the sweeper finds cold values. `cursor`: a scan over all keys that keeps its place between calls, so one pass checks each key one time. `random`: random samples, so keys can be checked many times and others not at all. | `cursor` (base), `random` |
| `compression-sweeper-samples` | Runtime | The most keys the sweeper checks in one cron call (10 calls per second at `hz 10`). With `cursor` also the most hash buckets it visits. It sets the main-thread work per call. | 100, 500 (base), 2000 |
| `compression-sweeper-backoff-seconds` | Runtime | `cursor` only: after a pass in which less than 1% of the checked keys could be compressed, the sweeper pauses for this many seconds. 0 turns the pause off. | 0, 60 (base) |
| `--save ''` | Startup, every run | No RDB snapshots, so no child process stops the sweeper during the run. | - |
| `--protected-mode no` | Startup, every run | Lets the client machine connect without a password. | - |
| `--maxmemory-policy allkeys-lfu` | Startup, every run | LFU eviction policy. Here it matters because the sweeper then uses the LFU counter to decide if a key is cold: a new key starts at 5 and is cold at 4 or less (`compression-lfu-threshold 4`), so it is hot for about 1 minute after it is written or read. | - |
