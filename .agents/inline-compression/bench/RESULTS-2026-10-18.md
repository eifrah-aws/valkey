# Inline compression benchmark - 2026-10-18

**Build:** `e89a8c20c` (branch `valkey-inline-compression`). **Raw data:** `results/20261018-103046/`. **Checked by:** `analyze.py` (all checks pass: run settings, request counts, INFO counter sums, and every number below computed again from the raw files).

**Setup.** Server: 64 cores, 123 GB, `allkeys-lfu`, `hz 10`, `--save ''`. Client: `sb`, 512 connections, 16 threads. Load: 5M `SET` over 1M keys (`github-events` JSON, about 2 KB each, 2.0 GB of values). Then 10 minutes of watching, then 4 runs of 5M `GET` at 100k rps, over 10%, 30%, 50% and 100% of the keys. Base settings: `--io-threads 12`, `lz4`, `compression-threads 12`, `compression-max-inflight-requests 1000`, `cursor`, 500 samples, backoff 60 s. Each scenario changes one setting.

## Findings

1. **Memory: -51%** for this data set, on all 1M keys, within about 6 minutes (cursor, 500 samples). The workers need only about 4.4 s of CPU for 1M values; `compression-threads` 4, 12 and 16 give the same speed.
2. **cursor is better than random.** For the same result it checks 2.8M keys, against 11.8M for random. With 500 samples, random reaches only 90% in 10 minutes. The sweeper costs about 9 s of main-thread CPU in 10 minutes (about 1.5% of one core).
3. **`compression-max-inflight-requests 100` (the default) is too low.** At `hz 10` it allows about 1,000 jobs per second, so only 49% was compressed in 10 minutes, the same as 100 samples. 1000 and 10000 give the same result.
4. **SET is not affected:** 880k-920k rps and p99 2.9-3.1 ms in all scenarios, because new keys are hot and are not compressed during the load.
5. **Reads of compressed keys cost latency.** Each first read decompresses the value on the main thread. At 100% touch, GET p99 is 2.4-2.8 ms against 0.46-1.05 ms on the baselines (2.5x-6x). At 10% touch the difference is small.
6. **A faster sweeper makes reads worse.** With 2000 samples, keys that cooled down during the earlier GET runs are compressed again and then decompressed again (1.5M decompressions against 1.13M). GET p99 reaches about 10 ms, and the client can not hold 100k rps.
7. **One full read removes the whole saving.** After the GET run over 100% of the keys, memory is back to 2.32-2.33 GB in every scenario (decompress on read keeps the plain value).
8. **The backoff does not show in 10 minutes:** cursor-base paused once, near the end (2.80M checks, against 2.98M without backoff). It saves work on stable data over longer times.
9. **io-threads:** 6 threads limit SET to about 710k-760k rps; 12 and 24 are the same.

## Recommendations

1. Keep `cursor` as the default policy, and keep 500 samples. 2000 compresses faster, but it hurts reads much more.
2. Raise the default of `compression-max-inflight-requests` from 100 to 1000.
3. Make read latency the next design topic. Options: decompress in the I/O threads (the off-loading idea in the plan), and a read of a cold key that returns a temporary copy and keeps the frame, so one scan does not undo the saving. This needs a decision and its own benchmark.
4. Before trusting small differences, run the main scenarios 3 times. The baselines alone vary from 0.46 to 1.05 ms GET p99 at 100% touch, and cursor-ct4 (1.38 ms) is not clearly better.
5. Add a longer run (for example 1 hour, no reads) to measure the backoff, and a run with a smaller value set, where the allocator rounding changes the saving (design doc, Appendix A).
